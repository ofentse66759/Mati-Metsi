 Security Requirements (Risk Assessment)
Mati-Metsi is a single-file, offline-first Progressive Web App of under 2MB that runs entirely in the browser. It has no server, no database and no third-party tracker. Accounts, reports, help listings, alert subscriptions, resilience-plan progress and drafts are stored in the browser's localStorage on the user's own device. The only outbound network calls are to WeatherAPI.com for live weather and geocoding, and to Open-Meteo for air quality; both receive only the suburb name a user types, never GPS coordinates or personal identifiers. Because there is no backend, several classic server-side risks do not exist in this phase — there is no server to breach, no database to inject into and no API key travelling in transit beyond the weather key itself. In exchange the app carries a different risk profile: the device is the trust boundary, localStorage is not encrypted at rest, and client-side password hashing is a demo-grade control rather than a production authentication scheme. The assessment below is therefore written for what the app actually is, not for a future version that has not shipped.

The high risks in this build are four. The first is home-address exposure through the free-text suburb field: a user could type a full street address without realising it, so the report form, the help board and the help message dialog all pass their text through a street-address regular expression (ADDRESS_RE) that matches a street number followed by a street-type word, and reject entries that look like a street address with a clear message. The second is fake or malicious reporting: a single user could fabricate an outage to mislead neighbours, so three independent community confirmations are required before a report is auto-promoted to Confirmed, a user cannot confirm their own report, and any status beyond "resolved" requires a verified-partner role rather than a normal account. The third is POPIA personal information stored locally: reports, names and suburbs are visible to anyone using the same device, so the profile page offers a one-click JSON export of everything the app holds about the user and a one-click "Delete account and all data" action that wipes accounts, reports, help listings, preferences, plan progress, drafts, location and previous score from the device; the Privacy Notice on the About page describes the scope and publishes the DPO email. The fourth is password storage: users type a password at sign-up, so passwords are hashed with SHA-256 via the Web Crypto API with a fixed salt before being written to localStorage — an honest limitation that is treated as demo-grade and is replaced by server-side Argon2id hashing when the backend ships in Phase 2. Beyond these, the help board carries a fraud risk because it is where a stranger might try to scam a neighbour; the board therefore blocks banking-detail patterns (BANKING_RE) and street addresses in the listing form, the message dialog and the listing title and description, and a safety banner above the board reminds users to meet in public places, never share banking details or PINs, and never pay upfront.

The medium risks are cross-site scripting through user-generated report descriptions and help titles — mitigated by a single escaping function that every user-controlled value passes through before it reaches the DOM, with no use of unescaped innerHTML, no eval, no new Function and no document.write; photo privacy, because a photo could carry EXIF GPS coordinates — mitigated by routing every uploaded image through a <canvas> redraw at a maximum of 900 pixels and re-encoding it as JPEG at 0.72 quality, which strips EXIF metadata including GPS by design rather than by accident; client-side storage tampering, where a technically skilled user can edit localStorage from DevTools — acknowledged as an out-of-scope limitation for the demo and stated plainly in the Privacy Notice, with server-side authority replacing client state as the source of truth in Phase 2; Weather API key exposure, since the key sits in the source and is therefore public, but WeatherAPI.com keys are rate-limited per plan and a stolen key exhausts a quota rather than losing data, so the mitigation is operational — a dedicated key on a low plan ceiling; and offline cache poisoning, which does not currently apply because no service worker is registered, and which will be scoped to static assets plus the last weather response only when the service worker is added in Phase 3. The low risks are denial of service, which is not applicable because there is no server to attack and the weather API's only shared resource is cached locally so a quota outage degrades gracefully to a "saved forecast" mode with a visible label, and demo-account abuse, which is intentional — the demo partner credentials are published for judging and will be removed from the production build. The security goals for this phase are therefore straightforward: confidentiality, meaning a user's name, email, suburb, plan progress and reports never leave the device; integrity, meaning a report cannot be marked Confirmed or Resolved by a single non-partner user and fake reports do not reach the high-severity alert band alone; availability, meaning the app runs fully offline after the first load and a weather API outage degrades gracefully to the last saved forecast with predictions continuing on community reports alone; and POPIA compliance through minimum data collection, no GPS, no trackers, one-tap export and one-tap deletion.
 Threat Modelling & Design Review
The threat model below is a STRIDE analysis written against the current build rather than against the planned backend. Spoofing is the first threat: an attacker creates a normal account and pretends to be a ward-disaster committee. The design control is that status changes beyond "resolved" require user.role === 'partner', and the role can only be set through a function that is explicitly labelled "demo" in the profile page — the honest position is that real partner verification is Phase 2, and every piece of partner-generated content carries a visible "Demo" pill so a reader can always tell the difference. Tampering is the second: a user edits their own report after submission, or edits localStorage in DevTools. The app-level control is that report history is append-only — every status change pushes a record of {status, at, by} and never overwrites the previous one, and there is no edit UI for reports — while storage tampering is acknowledged as a limitation of the local-only phase rather than being papered over. Repudiation is the third: a partner posts a public response and later denies it. Every partner response is stored in the report's responses array with the author, organisation, role, note and timestamp, and the partner dashboard keeps an append-only audit log recording every action with timestamp, actor and count. Information disclosure is the fourth: a user accidentally reveals a street address or banking details. Both patterns are blocked on every text field that could carry them, photo EXIF is stripped by the canvas redraw, no GPS API is called anywhere in the file, and the only outbound call carries a place name rather than the user's coordinates. Denial of service is the fifth: a user spams confirmations to manipulate the three-vote threshold, or the weather API is rate-limited. A user can only vote once per report because their email is stored in the votes array and toggled rather than appended twice, and a weather API failure falls back to a cached forecast with an explicit status label. Elevation of privilege is the sixth: a normal account tries to move a report to Confirmed or Resolved. The status function checks for partner role or for the report owner acting on their own report and only to the Resolved state, and the partner-only response function returns early for any non-partner, so a community user can only resolve their own report and nothing else.

The architecture review of the current build is short because the build itself is short. A single .html file with no build step contains the theme tokens, the nine hash-routed views in one document, and a main script plus nine feature modules. The script writes to localStorage for accounts, reports, help listings, alerts, plan progress and drafts; uses the Web Crypto API to hash passwords; uses the Canvas API to downscale photos and strip their metadata; and calls out to WeatherAPI.com for the current and three-day forecast and to the Open-Meteo geocoding and air-quality endpoints through an in-page adapter that routes place names to the Weather API. What is deliberately not present in the build is equally important to state: there is no Supabase integration, no WhatsApp Cloud API, no SAWS or Rand Water feed, and no service worker, all of which are on the roadmap as Phases 2 through 4 rather than claimed as shipped. The deliberate omissions in the code are that there is no localStorage write of a raw password, no eval, new Function, unescaped innerHTML on user content, document.write or inline event handler on a dynamic node, no third-party analytics, ad network or session-replay script, and no call to navigator.geolocation anywhere in the file.
 Development (Secure coding practices)
The frontend applies input validation to every user-controlled field. Names and emails are length-capped and checked against an email regular expression on both the browser and the submit handler; suburbs are capped at 100 characters and checked against the address pattern before submission; help listings run through the banking-detail pattern that blocks mentions of bank details, PINs, OTPs, EFTs and account numbers; severity is a radio button rather than free text; report descriptions are constrained to between five and one thousand characters by both the HTML attributes and the submit handler; and phone numbers must match a nine-to-fifteen digit pattern after stripping non-numeric characters. Cross-site scripting prevention rests on a single escaping function that HTML-entity-encodes every dynamic value before it is inserted into the DOM, with no unescaped innerHTML assignment of user data and no user content ever being evaluated as script. Password handling is deliberately honest about its limits: passwords are hashed with SHA-256 through crypto.subtle.digest() with a fixed salt before being written to localStorage, and the Privacy Notice and this document both state that this is demo-grade, that a production system must hash on the server with a slow memory-hard function such as Argon2id, and that this limitation is removed in Phase 2 when Supabase Auth takes over. Sessions are a mm_user entry in localStorage containing name, email, role, organisation and a sign-in timestamp rather than a JWT, and the same honest limitation applies: a client-side session can be forged by anyone with DevTools access, and the demo-partner credentials are public by design for judging. The "Remember me" checkbox is respected through a session-scoped flag in sessionStorage, so if the box is unchecked the session is cleared when the tab closes.

Photo handling is one of the app's genuine security controls and is worth describing in full. Uploads are type-checked against the image/* pattern, size-checked at eight megabytes before any read begins, and then processed through a FileReader, an Image and a <canvas> at a maximum of 900 pixels on the longest side before being re-encoded as JPEG at 0.72 quality. The EXIF block, including any GPS coordinates the camera recorded, is not preserved through the canvas redraw, so a photo that is taken on a GPS-enabled phone cannot leak the household's location through its metadata — this is a deliberate privacy control rather than an incidental effect, and it is what makes the "avoid faces and number plates" hint on the upload form meaningful rather than decorative. The resulting data URL lives only in localStorage and is never uploaded anywhere in the current build. Offline-first behaviour is protected by three separate mechanisms. Weather responses are cached in mm_weather_cache and the app reads from that cache whenever the API is unreachable, showing the phrase "showing the forecast for [place] saved [time ago]" so the user knows they are looking at stale data rather than fresh. Reports, drafts, plan progress and help listings persist across reloads. And an offline outbox queues any report written while the device is offline and sends it on reconnect, so a user who loses signal mid-report does not lose the report. Graceful failure is applied throughout: every localStorage call is wrapped in a try/catch so a full or blocked storage does not crash the app, a report that fails to save because storage is full is retried without the photo and the user is told, and an unavailable weather API produces an explicit cached or error state rather than a silent failure. The backend section of this document is short because there is no backend in this phase; the security trade-offs of that choice are stated plainly — no server means no server breach surface, but it also means no server-side rate limiting, no server-authoritative authentication and no encrypted-at-rest storage. The Phase 2 design for Supabase will include Row Level Security on every table, server-side authentication with short-lived JWTs and server-side password hashing, server-side input validation mirrored from the client controls, an edge rate limiter for report and confirmation endpoints, a service role key stored only in Vercel environment variables, and private Storage buckets with server-side EXIF stripping. The POPIA position of the current build follows from the architecture: minimum data collection of name, email, suburb and an optional phone number on a help listing, with no ID number, no date of birth and no address; no GPS collection anywhere in the code; one-click JSON export from the profile page containing the user, account, own reports, own help listings, confirmations given, preferences, plan, draft, location and previous score; one-click account deletion that removes the user's account, their reports with their votes stripped from other users' reports, their help listings, and all preference, plan and draft state from the device; no third-party trackers, no advertising and no data sales; a published DPO contact in the Privacy Notice and the footer; and a breach protocol that will be documented and tested for POPIA Section 22 once Phase 2 ships, because a breach of a Mati-Metsi server is not currently possible when no personal data leaves the device.
 Security Testing
The static checks performed before submission were manual, and they are reported as manual rather than dressed up as an automated pipeline. Every localStorage key that the app writes — accounts, user, reports, help, alerts, preferences, plan, draft, demo, weather cache, location, previous score, outbox, events, audit, weights, organisation and shared store — was opened in DevTools after every feature path and checked for anything that should not be there, and the confirmed result is that no plaintext passwords, no GPS coordinates and no other user's personal details are present. A search of the file for dangerous sinks confirmed zero occurrences of eval, new Function, innerHTML on user data, document.write, dangerouslySetInnerHTML and navigator.geolocation, and confirmed that no inline event handlers are attached to dynamically generated content. A secrets scan found one secret in the file, the WeatherAPI.com key, which is disclosed and mitigated operationally rather than hidden; the Supabase URL and service-role key are not in the current build because there is no Supabase integration yet. The file was loaded in Chrome, Firefox and Safari and the console showed no errors on a fresh load with the demo data seeded. The dynamic tests were equally manual and each of them was run against the live app rather than simulated. Confirming your own report is blocked by the early return in the vote function. Changing a report's status as a community user is blocked by the role check. Submitting a report with a street address such as "123 Main Street" in the suburb field is rejected with the message "Please enter your suburb or community only." Submitting a help listing that mentions bank details is rejected by the banking pattern. Submitting a help message containing a street address is rejected before the message is stored. Uploading a ten-megabyte photo is rejected with "Photo is too large (max 8 MB)." Uploading a PDF disguised as a photo is rejected by the image type check. Reloading the page while offline was verified to keep the app working with a visible "saved forecast" label and an offline banner. Submitting a report while offline was verified to queue it in the outbox and send it on reconnect. Inspecting localStorage.mm_accounts after a sign-up confirmed that the stored value is a SHA-256 hex hash rather than a plaintext password. The "attempt to reach a Supabase endpoint" test does not apply in this phase because there is no Supabase integration in the build.

The known limitations of this build are reported honestly rather than hidden, because a security document that claims more than it delivers is worse than one that states its limits. Client-side password hashing is not a security boundary — anyone with DevTools can edit localStorage to impersonate any account, and this is true of any client-only app; it is stated in the Privacy Notice and in this document rather than being quietly ignored. The demo-partner credentials are public, because they are printed on the login screen for judging, and the "Verified partner role (demo)" card in the profile page is labelled accordingly; they will be removed from the production build. There is no server-side rate limiting, so a user can submit reports at whatever pace they type; the mitigations available in this phase are community consensus through the three-confirmation threshold and duplicate detection through word-similarity, not rate limiting. localStorage is not encrypted at rest, so a stolen device exposes the user's own reports and plan progress; this is disclosed in the Privacy Notice. And the Weather API key is in the source, which is mitigated only by rate-limiting on the provider side. What has not yet been tested is as important as what has: Row Level Security policies on Supabase, server-side authentication and session management, edge rate limiting on the report and confirmation endpoints, server-side EXIF stripping verified with ExifTool, and a breach-notification drill for POPIA Section 22 are all Phase 2 work and are scheduled against the backend that makes them meaningful.
 Assessment & Secure Integration
The current architecture gets several things right, and it gets them right by design rather than by accident. The most significant is that there is no server and therefore no server breach — the biggest class of data-breach risk in a community app is a stolen backend, and this build does not have one, so the risk is transferred to the device where the user has direct control and a one-tap delete. The second is that GPS is never collected: navigator.geolocation is not called anywhere in the file, and the only place name sent to any external service is what the user types in the weather field, which is a strong POPIA position and a genuine differentiator against apps that quietly collect location. The third is that every user-controlled sink is escaped through a single function, with no eval and no unescaped innerHTML, so the classic XSS surface is closed rather than merely narrowed. The fourth is that the risky actions are role-gated: a community user cannot move a report to Confirmed or In Progress, only the owner can mark a report Resolved, and only a partner can post a public response. The fifth is that status changes and partner responses are appended with an {at, by} timestamp and never overwritten in the app logic, which supports audit and repudiation analysis. The sixth is that the app degrades gracefully, working offline, tolerating a full storage quota, falling back to a cached weather forecast and never breaking when an external API fails. What is deliberately not yet implemented is equally important to state. There is no server-side authority; in a future phase the source of truth moves from localStorage to Supabase with Row Level Security, and until then the client state is the state. There is no production-grade authentication; client-side SHA-256 is demo-grade and is replaced by Supabase Auth with server-side Argon2id hashing and server-managed JWTs in Phase 2. And there is no server-side rate limiting, EXIF stripping or breach-notification drill; all three are scheduled for Phase 2 alongside the backend itself rather than being claimed today.

The security work planned for each phase follows directly from what the current phase cannot do. Phase 1, the current build, delivers client-side validation, the single escaping function that closes the XSS surface, the ADDRESS_RE and BANKING_RE privacy guards, SHA-256 password hashing, canvas-based EXIF stripping on every photo, the offline fallback, and the POPIA export and delete actions. Phase 2, the Supabase backend, adds Row Level Security on all tables, server-side password hashing with Argon2id, server-side input validation mirrored from the client controls, edge rate limiting on the report and confirmation endpoints, private Storage buckets with server-side EXIF stripping, a server-side append-only audit table, and a documented and tested POPIA Section 22 breach-notification procedure. Phase 3, push notifications and the WhatsApp and SMS channels, adds X-Hub-Signature-256 verification on the WhatsApp Cloud API webhook, a per-number rate limit of ten messages per minute, server-side storage of opt-in consent with a timestamp, and an SMS fallback routed through a vetted gateway. Phase 4, the official data feeds, consumes the SAWS feed read-only with no write path, sources Rand Water reservoir data under a documented data-sharing agreement, and labels every external data point in the UI with its source and freshness. Phase 5, the aggregate insights that make the business model work, uses strictly non-personal aggregation, applies small-cell suppression at a k-anonymity threshold of ten before any dataset leaves the backend, and requires a POPIA-compliant data-sharing agreement for every partner whose data would be included. The security posture of the current build is therefore appropriate for its phase: a single-file, no-backend demo that minimises its attack surface by not having a server, does not collect GPS, does not ship with trackers and hands the user one-tap export and delete. Its honest limits — client-side hashing, no server-side rate limiting and demo-visible partner credentials — are stated in the app's own Privacy Notice and in this document rather than buried, and every control listed for Phase 2 is scoped, mapped to a POPIA or OWASP requirement, and scheduled against the backend work that will make it real.
